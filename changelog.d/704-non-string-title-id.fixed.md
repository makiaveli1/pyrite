- **A `title:` that YAML reads as a number, boolean or date is indexed under its own id (#704).** The title is now stringified once, where the file is loaded, so the id, the stored title and `get` agree: `title: true` → id `true`, stored title `"true"` (not SQLite's `"1"`); `title: 2024` → `2024`; `title: 1e3` → `1000-0`. A `title:` that is a list, mapping or NaN gets no id: loading refuses it with a named reason (`title must be a string, got a list`), including when the file has an explicit `id:` line (that case used to crash the index write with a `sqlite3.ProgrammingError`); the index skips the file and `ids missing` lists it as skipped with that reason (#711). Limits: the id comes from the value YAML parsed, not the source text, so spellings that parse equal (`1.10` and `1.1`, `1e3` and `1000.0`, `.inf` and `-.inf`, both `inf`) collide, and `ids missing` reports the collision. A title YAML reads as falsy (`false`, `0`, `0.0`, `-0`) keeps the `entry-da39a3ee` empty-title id it had before, so an upgrade moves no id and breaks no link; its stored title is the stringified value (`"0"`, `"false"`), and two such files share that one id, which `ids missing` reports as a collision. `schema validate` now reports an `id_collision` for two files with falsy titles and no id, since they do share `entry-da39a3ee`. A file with an explicit `id: x` and a refused title is still found by `find_file("x")`, because reading an explicit id does not build the entry, so `create` says the id is taken while `get` says not found; #777 (ENTRY_UNREADABLE) owns that case.
